Everything below was run on 2026-11-18 on a Fedora 44 Cloud Edition virtual
machine (systemd 259, SELinux enforcing, firewalld 2.4.4, OpenSSH 10.2), with a
build of tui-secure from its main branch ahead of 1.0.0, including
[tui-secure#32](https://github.com/tui-tools/tui-secure/pull/32). The tool ran
as an ordinary user, `lab`, in a terminal reached over SSH, and escalated with
`sudo -n`. The screens and dialogs are copied from the terminal, without the
dialog borders and with the runs of spaces in wide tables shortened; nothing in
them was retyped. The screenshot is the tool's own, from `--demo`.

tui-secure does not try to fix everything it finds. Most findings belong to
another tool in the family, and the fix column says which one. What it fixes
itself is small and is shown as the file it will leave behind.

The build here still called tui-update and tui-users "(planned)" in the fix
column, from before they shipped; 1.0.0 names them plainly, in `--check`'s
`fix.tool` too.

The score weighs an `ok` as one, a `warn` as half and a `bad` as nothing.
`enter` on a row shows the evidence: each command the probe ran and the line
of its output that decided the verdict. `tui-secure --check` prints the same
probes as JSON, for a script or a monitoring job.

The firewall row is worth a sentence. Over SSH, polkit refuses `firewall-cmd`
to an ordinary user, and before tui-secure#32 the probe read that refusal as
"firewalld is installed but not running" and scored a running firewall as
`bad`. It now asks again through `sudo -n`, and when that is refused too, it
reads the unit's state from systemd and says the zone could not be read.

## The kernel keys (`a`)

On the Kernel hardening row, `a` lists one fix per key below the recommended
value:

  title="a on Kernel hardening"

   Set fs.protected_regular=2, now and on every boot

Each one is shown as the whole file it leaves, then the two commands:

<OutputBlock

## After a reboot

`sysctl -w` changes the running kernel; the file is what makes it last. After
`sudo -n systemctl reboot`:

<CommandDialog
  title="Check it again"
  command="sysctl kernel.kptr_restrict fs.protected_regular fs.suid_dumpable"
/>

<OutputBlock
  title="Its output"
  body={`kernel.kptr_restrict = 1
fs.protected_regular = 2
fs.suid_dumpable = 0`}
/>

`tui-secure --check` then put the score at 69, with the kernel probe `ok`.

## Undo

The file is the only thing the kernel fixes write, and its own first lines say
how to take a line back: remove it and run `sudo sysctl --system`. That was not
done on this machine.

## What this does not show

- The SSH and listening ports fixes (`a` on those rows), and the firewall
  fixes on a machine whose firewall is off.
- Debian, Ubuntu and Omarchy Server, where the firewall is ufw and the MAC
  layer AppArmor or none.
- The findings it hands to other tools: [tui-update](/tools/tui-update/),
  [tui-users](/tools/tui-users/) and [tui-ssh](/tools/tui-ssh/) are where
  those are fixed.

More on every probe is on the [tui-secure page](/tools/tui-secure/) and in the
[README](https://github.com/tui-tools/tui-secure/blob/main/README.md).
