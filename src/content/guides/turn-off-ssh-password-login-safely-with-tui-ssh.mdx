Everything below was run on 2026-10-23 with
[tui-ssh v0.2.4](https://github.com/tui-tools/tui-ssh/releases/tag/v0.2.4),
installed from the tui-tools apt repository, on an Ubuntu 24.04.5 container
running systemd and openssh-server `1:9.6p1-3ubuntu13.20` (OpenSSH 9.6). The
server is `198.51.100.10`; a second container, `198.51.100.20`, played the
laptop that logs in and the stranger that guesses passwords. The screens and
dialogs are copied from the terminal, without the dialog borders and with the
runs of spaces in wide tables shortened; nothing in them was retyped. The
screenshot is the tool's own, from `--demo`.

The order matters more than the setting. Turning off passwords on a server
where nobody has a working key is how people lock themselves out, so the key
comes first and the switch comes second.

## Install and open it

The one-time repository setup is on the [install page](/install/). After it:

<CommandDialog
  title="On Debian and Ubuntu, after the one-time repository setup"
  command="sudo apt update -qq && sudo apt install -y tui-ssh"
  tool="tui-ssh"
  manager="apt"
/>

`tui-ssh --version` printed `tui-ssh 0.2.4`.

The settings screen is only as good as `sshd -T`, which needs root. tui-ssh
asks for it through `sudo -n`, which never prompts. On this Ubuntu machine,
`sudo -v && tui-ssh` in the same terminal was not enough: the tool started with
`config: from files` in its header, and the service screen said:

<OutputBlock
  title="Screen 5, started as an ordinary user after sudo -v"
  body={`config read  sudo needs a password: run \`sudo -v\` in another terminal, then retry`}
/>

Starting it with sudo gave the server's own answer, and the header said
`config: effective`:

<CommandDialog title="Start it as root" command="sudo tui-ssh" />

## The starting point

On machines that cloud-init provisions with password login on, a file named
`/etc/ssh/sshd_config.d/50-cloud-init.conf` sets `PasswordAuthentication yes`.
To see what tui-ssh does about a file like that, one was created here by hand,
as root:

<CommandDialog
  title="A stand-in for the cloud-init file"
  command={`echo "PasswordAuthentication yes" > /etc/ssh/sshd_config.d/50-cloud-init.conf`}
/>

Screen `1` puts the settings that decide who gets in first, each with a verdict
and the file and line that set it:

<OutputBlock
  title="sudo tui-ssh, screen 1 (the first rows)"
  body={`service: ssh running   config: effective   findings: 6   sessions: 0   backend: openssh 9.6
SETTING                                 VALUE                 SET AT
PermitRootLogin                         without-password ok   (default)
PasswordAuthentication                  yes              !!   /etc/ssh/sshd_config.d/50-cloud-init.conf:1
PubkeyAuthentication                    yes              ok   (default)
KbdInteractiveAuthentication            no               ok   /etc/ssh/sshd_config:71
PermitEmptyPasswords                    no               ok   (default)`}
/>

`without-password` is the older spelling of `prohibit-password`, and it is
what this sshd prints for the default: root by key only.

## Check who has a key (`6`)

Screen `6` lists `root` and every account with a real shell, one row per key in
its `~/.ssh/authorized_keys`, and a row saying so when there is none:

<OutputBlock
  title="Screen 6, before"
  body={`USER       TYPE      FINGERPRINT              COMMENT
root       —         (no authorized key)      —
ana        —         (no authorized key)      —

Nobody. With passwords off, nobody would get in over SSH. The key for `ana` was

## Add it (`A`)

`A` asks for the account, then for the `.pub` line. After `enter` the pasted
line is staged and read back by `ssh-keygen` before anything is written:

<OutputBlock
  title="A, account ana, the key pasted, enter"
  body={`Add a public key to ana

✓ ssh-keygen reads the new key as 256 SHA256:opFX7OcKabidP8DGf66Mi5Hj2DX4tH7InnxEIJ7xYNQ ana@laptop (ED25519)

Whoever holds the private half of SHA256:opFX7OcKabidP8DGf66Mi5Hj2DX4tH7InnxEIJ7xYNQ can then log in as ana, from anywhere the firewall allows.

--- /dev/null
+++ /home/ana/.ssh/authorized_keys
@@ -1,0 +1,1 @@
+ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIOxnHRWZJMWsvePdF8mObeI4oS2fr2A+2M91KEkD32rz ana@laptop

Command to run:
$ install -d -m 700 -o ana -g ana /home/ana/.ssh
$ install -m 600 -o ana -g ana /tmp/tui-ssh-2013124891/authorized_keys /home/ana/.ssh/authorized_keys`}
/>

The fingerprint matches the one the laptop printed. After `y`, the row for
`ana` showed `ED25519   SHA256:opFX7OcKabidP8DGf66Mi5Hj2DX4tH7InnxEIJ7xYNQ   ana@laptop`.
Test it from the laptop while passwords still work, not after:

<CommandDialog
  title="On the laptop"
  command={`ssh -o BatchMode=yes ana@198.51.100.10 'id; echo $SSH_CONNECTION'`}
/>

<OutputBlock
  title="Its output"
  body={`uid=1001(ana) gid=1001(ana) groups=1001(ana),27(sudo)
198.51.100.20 59324 198.51.100.10 22`}
/>

`deploy` still has no key. On a real server, that row is the moment to add one
or to accept that the account stops logging in over SSH.

## Turn off passwords (`e`), and the Include-order warning

On screen `1`, `PasswordAuthentication` selected, `e` opens the editor with the
current value and where it came from. `tab` to the value, `→` to `no`, then
`enter`. The staged file is checked by sshd before the question is asked, and
this time the dialog has something to say about it:

<OutputBlock
  title="e on PasswordAuthentication, value no, enter"
  body={`Set PasswordAuthentication to no

✓ accepted by sshd -t -f /tmp/tui-ssh-3216292431/90-tui-ssh.conf

PasswordAuthentication is already set at /etc/ssh/sshd_config.d/50-cloud-init.conf:1, which sshd reads before this drop-in — and it takes the FIRST
value it is given, so what is written here would be read and ignored. Change it there instead.

--- /dev/null
+++ /etc/ssh/sshd_config.d/90-tui-ssh.conf
@@ -1,0 +1,5 @@
+# Written by tui-ssh, and rewritten whole on every change.
+# sshd takes the FIRST value it is given for a keyword, so a keyword set
+# above this file's Include in /etc/ssh/sshd_config wins over what is here.
+
+PasswordAuthentication no

Command to run:
$ install -m 600 /tmp/tui-ssh-3216292431/90-tui-ssh.conf /etc/ssh/sshd_config.d/90-tui-ssh.conf
$ systemctl reload ssh`}
/>

`50-cloud-init.conf` sorts before `90-tui-ssh.conf`, so sshd reads it first.
The warning does not block the write. `y` was pressed anyway, to see what
happens, and `enter` on the row afterwards showed both files and which one
sshd uses:

<OutputBlock
  title="enter on PasswordAuthentication, after y"
  body={`PasswordAuthentication
  value          yes
  read from      \`sshd -T\`, which is the server's own answer
  verdict        risk
  every account with a password is something a stranger can guess at.
Written at
  wins  /etc/ssh/sshd_config.d/50-cloud-init.conf:1   PasswordAuthentication yes
        /etc/ssh/sshd_config.d/90-tui-ssh.conf:5   PasswordAuthentication no`}
/>

A tool that showed the files instead of `sshd -T` would have looked done here.
The fix goes where the warning said, in a second terminal:

<CommandDialog
  title="Remove the file that wins"
  command="sudo rm /etc/ssh/sshd_config.d/50-cloud-init.conf"
/>

`ctrl+r` re-read the server, and the row became `no   ok
/etc/ssh/sshd_config.d/90-tui-ssh.conf:5`. That is what sshd will do on its
next reload, not what the running daemon is doing: `sshd -T` reads the files.
A guess from the laptop at that moment still got a password prompt:

<CommandDialog
  title="On the laptop"
  command="sshpass -p guess123 ssh -o PubkeyAuthentication=no deploy@198.51.100.10 true; echo exit=$?"
/>

<OutputBlock title="Before the reload" body={`Permission denied, please try again.
exit=5`} />

`r` reloads the service, with its own preview (`$ systemctl reload ssh`).
After `y`, the same command from the laptop:

<OutputBlock title="After the reload" body={`deploy@198.51.100.10: Permission denied (publickey).
exit=255`} />

## Root and keyboard-interactive (`e` again)

`PermitRootLogin` goes the same way. `space` on the value opens the list of
what sshd accepts: `no`, `prohibit-password`, `forced-commands-only`, `yes`.
With `no`, the drop-in now exists, so the dialog is a diff against it:

<OutputBlock
  title="e on PermitRootLogin, value no, enter"
  body={`Set PermitRootLogin to no

✓ accepted by sshd -t -f /tmp/tui-ssh-1105772857/90-tui-ssh.conf

--- /etc/ssh/sshd_config.d/90-tui-ssh.conf
+++ /etc/ssh/sshd_config.d/90-tui-ssh.conf
@@ -4,2 +4,3 @@

 PasswordAuthentication no
+PermitRootLogin no

Command to run:
$ install -m 600 /tmp/tui-ssh-1105772857/90-tui-ssh.conf /etc/ssh/sshd_config.d/90-tui-ssh.conf
$ systemctl reload ssh`}
/>

`KbdInteractiveAuthentication` was already `no`, from line 71 of Ubuntu's
`sshd_config`. It was written to the drop-in as well, so the setting no longer
depends on a line in a file the package owns. Ubuntu's `Include` sits at the
top of `sshd_config`, so the drop-in is read first and there was no warning;
`enter` on the row afterwards marked `90-tui-ssh.conf:7` with `wins` and
listed `sshd_config:71` under it.

## Check it from a shell

<CommandDialog
  title="The file, and what sshd says"
  command={`sudo cat /etc/ssh/sshd_config.d/90-tui-ssh.conf; sudo sshd -T | grep -Ei "^(passwordauthentication|permitrootlogin|kbdinteractiveauthentication) "`}
/>

<OutputBlock
  title="Its output"
  body={`# Written by tui-ssh, and rewritten whole on every change.
# sshd takes the FIRST value it is given for a keyword, so a keyword set
# above this file's Include in /etc/ssh/sshd_config wins over what is here.

PasswordAuthentication no
PermitRootLogin no
KbdInteractiveAuthentication no
permitrootlogin no
passwordauthentication no
kbdinteractiveauthentication no`}
/>

## Prove it from outside

From the laptop, with a terminal:

<CommandDialog
  title="On the laptop"
  command={`ssh -o PubkeyAuthentication=no deploy@198.51.100.10
ssh -o PubkeyAuthentication=no ana@198.51.100.10
ssh ana@198.51.100.10 hostname`}
/>

<OutputBlock
  title="Their output"
  body={`deploy@198.51.100.10: Permission denied (publickey).
ana@198.51.100.10: Permission denied (publickey).
web1`}
/>

No password prompt at all, even for `ana`, who has one. The server only offers
keys now:

<CommandDialog
  title="On the laptop"
  command={`ssh -v -o PubkeyAuthentication=no ana@198.51.100.10 2>&1 | grep "can continue"`}
/>

<OutputBlock title="Its output" body="debug1: Authentications that can continue: publickey" />

A session opened from the laptop afterwards (`ssh -tt ana@198.51.100.10
sleep 90`) showed up on screen `2` with its address, its terminal and its
logind session, which `t` would end. Keep one like it open while you change
any of this.

## Who is knocking (`3`)

Before the change, the laptop guessed passwords five times, three times for a
real account and twice for accounts that do not exist:

<CommandDialog
  title="On the laptop, before passwords were off"
  command="for u in deploy deploy deploy admin oracle; do sshpass -p guess123 ssh -o PubkeyAuthentication=no $u@198.51.100.10 true; echo exit=$?; done"
/>

Screen `3` reads `journalctl -u sshd -u ssh` for the last 24 hours (`w`
switches to 7 days). The header counts the failures:

<OutputBlock
  title="Screen 3, after the hardening (newest first)"
  body={`service: ssh running   config: effective   findings: 5   sessions: 0   failed 24h: 6   backend: openssh 9.6
WHAT          USER        FROM               METHOD
accepted      ana         198.51.100.20      publickey
accepted      ana         198.51.100.20      publickey
failed        deploy      198.51.100.20      password
failed        oracle      198.51.100.20      password
invalid-user  oracle      198.51.100.20      —
failed        admin       198.51.100.20      password
invalid-user  admin       198.51.100.20      —
failed        deploy      198.51.100.20      password
failed        deploy      198.51.100.20      password
failed        deploy      198.51.100.20      password
accepted      ana         198.51.100.20      publickey`}
/>

The sixth failure is the guess made between removing the cloud-init file and
the reload. The refusals after the reload are not on the list: sshd logged them
as `Connection closed by authenticating user deploy 198.51.100.20 port 44850
[preauth]`, not as failed passwords, because no password was ever tried.

`enter` on a row shows the line as it was logged:

<OutputBlock
  title="enter on the oracle row"
  body={`The line as it was logged
  2026-10-23T17:49:28+00:00 web1 sshd[992]: Failed password for invalid user oracle from 198.51.100.20 port 57022 ssh2
Read from
  journalctl -u sshd -u ssh --since -24h
  press b to block 198.51.100.20 at the firewall`}
/>

`b` blocks an address only through `ufw`, and only when `ufw` is running. Here
it is not, and `b` said so on the status line:

<OutputBlock
  title="b on the oracle row"
  body="no ufw on this machine to block 198.51.100.20 with — tui-firewall drives the one you do have"
/>

## Undo

tui-ssh owns one file. To go back to how the machine was before (without the
stand-in cloud-init file):

<CommandDialog
  title="Remove the drop-in and reload"
  command={`sudo rm /etc/ssh/sshd_config.d/90-tui-ssh.conf
sudo systemctl reload ssh
sudo sshd -T | grep -Ei "^(passwordauthentication|permitrootlogin) "`}
/>

<OutputBlock title="Its output" body={`permitrootlogin without-password
passwordauthentication yes`} />

The key added with `A` stays; `R` on screen `6` removes it, by fingerprint.

## What this does not show

- `Match` blocks (`m`), for keeping passwords on for one account or address.
- Host keys (`4`) and the service screen (`5`).
- Blocking an address: there was no `ufw` on this machine. See
  [tui-firewall](/tools/tui-firewall/) for the firewall itself.
- A real cloud-init machine. The `50-cloud-init.conf` here was written by hand
  to stand for one; what tui-ssh read and warned about is the same either way,
  because it reads the include order from the machine.

More on every screen is on the [tui-ssh page](/tools/tui-ssh/) and in the
[README](https://github.com/tui-tools/tui-ssh/blob/v0.2.4/README.md).
